# Heartfall 💔 ("Don't Break the Heart", `dont-break-the-heart`)

*Take turns removing glass pieces. Don't break the heart!*

A turn-based two-player game for Gulaab video calls.

- **Built with:** React 19, TypeScript and plain CSS. React is the only runtime dependency.
- **Nothing external:** no network calls, external assets or fonts, sound, ads or trackers.
- **Graphics:** everything is drawn with inline SVG, CSS and emoji.

## Rules

- **The heart:** a glass heart made of **12 pieces**. **9 are safe** and **3 are fragile**. Nobody can see which are which.
- **Turns:** players take turns tapping **one** piece per turn. The turn always passes to the other player after a tap.
- **Safe pieces** disappear with a sparkle.
- **Fragile pieces** crack the heart. The heart shakes, a crack spreads across it, and the cracked piece can't be picked again.
- **Breaking:** the heart withstands **2 cracks**. Whoever selects the **3rd fragile piece** shatters the heart and **loses**, and the other player **wins**.
- **Draw:** if all 12 pieces are removed without a 3rd crack, the round is a draw.
  - With exactly 3 fragile pieces this can't actually happen, because picking all 12 pieces always includes all 3 fragile ones.
  - The draw rule is implemented and tested on a configuration with fewer fragile pieces.
- **Scoring:**
  - A win scores **1 point**. A loss or a draw scores 0.
  - Scores carry over through **Play Again** and reset when a player leaves.
- **Who starts:**
  - Round 1: the host starts.
  - Round 2: the guest starts.
  - Round 3: the host again, and so on.

## How to play

1. Open the game; the host's heart is set up automatically.
   - The host sees *"Waiting for the other player..."* until the guest's game connects.
   - The guest sees *"Waiting for [host] to set up the heart…"* until the configuration arrives.
2. On *"Your Turn 💗"*, tap any glass piece.
3. Watch the **heart strength** below the heart (♥ ♥ ♥ → 💔 ♥ ♥ → 💔 💔 ♥) and try not to pick the third fragile piece.
4. When the heart breaks, the result card shows:
   - the winner and the loser
   - the score
   - **Play Again** and **Exit** buttons
5. **How to Play?** shows the rules at any time. **Exit** leaves the game.

## Message actions

These are all the actions the game uses, and all of them are listed in `meta.actions`:

| Action | Direction | Payload |
| --- | --- | --- |
| `start` | host → guest | **Configuration / snapshot:** `{ gameId, round, fragilePositions: number[3], firstPlayer, moves: number[], scoreHost, scoreGuest, rematch }` |
| `start` | guest → host | **Hello:** `{ hello: true, gameId, player: "guest", sync }`. Means *"I'm here"*; with `sync: true` it also means *"please send the snapshot"*. |
| `move` | guest → host | **Request:** `{ gameId, round, moveId, player, pieceIndex, crackCount, remainingPieces }`. The counts are the board as the guest sees it **before** the move. |
| `move` | host → guest | **Confirmed move:** same fields. The counts are the board **after** the move. |
| `rematch` | either | `{ gameId, round, player }` |
| `leave` | either | `{ gameId, player }` |

The fields in more detail:

- **`gameId`:** generated by the host each time its copy of the game opens. It grows over time, so a re-opened game is recognisably newer than the old one.
- **`round`:** counts rematches.
- **`moveId`:** the index of the move within the round.
- **Old-message protection:** together, these three identify stale and duplicate messages.

**Message size:** every message is well under 512 bytes; the largest, a full snapshot, is about 230 bytes. The game also refuses to send anything of 512 bytes or more.

**Message rate:** messages are only sent when a player does something, so the game stays far below 10 messages per second.

Example messages:

```json
{"action":"start","gameId":1793001234567123,"round":1,"fragilePositions":[2,7,10],"firstPlayer":"host","moves":[],"scoreHost":0,"scoreGuest":0,"rematch":false}
{"action":"move","gameId":1793001234567123,"round":1,"moveId":0,"player":"host","pieceIndex":4,"crackCount":0,"remainingPieces":11}
{"action":"rematch","gameId":1793001234567123,"round":1,"player":"guest"}
{"action":"leave","gameId":1793001234567123,"player":"host"}
```

## Multiplayer behaviour (host-authoritative)

**The host's role:**

- It is the only device that generates randomness: the fragile positions for every round, and the game id.
- It sends the configuration to the guest in a `start` snapshot, and both phones use exactly that configuration.

**What the host checks** for every guest move request:

- the game id and round
- the move index
- that it is the guest's turn
- that the piece exists and is still available
- that the guest's crack count and remaining pieces match the host's board

If the request is valid, the host applies it and broadcasts the confirmed move. If it isn't (out of turn, already used, stale, conflicting or malformed), the host rejects it and re-sends its snapshot so the guest's screen catches up.

**The guest never decides on its own whether a move is valid:**

- When the guest taps a piece, the move is only sent as a request. That piece pulses ("Placing your move…") until the host confirms it, and the confirmed board only changes when the confirmation arrives.
- If no confirmation arrives within 3 seconds, the guest drops its request and asks for a snapshot (`sync: true`). The game can't get stuck.

**How the guest checks confirmations:**

- The guest replays each confirmed move with the shared configuration.
- It requires the crack count and remaining pieces to match the host's.
- If anything doesn't add up, or a move is missing, it asks for a fresh snapshot.

**Ignored messages:**

- duplicate confirmations (same `moveId`)
- messages from older rounds or older games
- malformed messages and unknown actions

**Keeping the phones identical:** both render the same confirmed state, which is rebuilt from `(configuration, moves)`. The test suite compares the two boards after every move.

**One move per turn:**

- Once the host taps a piece, the turn passes immediately.
- The guest is locked while its request is pending.
- Removed pieces have no touch target.

> **The fragile positions are hidden, not secret.** Both phones hold them in memory so they can draw cracks the moment a piece is picked. They are never shown in the game, but a player inspecting their own device's memory could find them. They are not cryptographically protected.

## Rematch behaviour

- After a round ends, either player taps **Play Again**. This sends `rematch` and shows *"Waiting for [name] to agree…"*. The other player sees *"[name] wants to play again!"* and an **Accept & Play** button.
- A new round starts **only when both players have agreed**, and the host is the one that creates it:
  - new random fragile pieces
  - round + 1
  - the starting player alternates
  - the heart and the cracks reset
  - **the scores carry over**
  
  The host then sends the new configuration as a `start` snapshot.
- **Duplicate taps:** repeated **Play Again** taps, duplicated `rematch` messages, or both players tapping at the same time create exactly **one** new round.
- **Old messages:** messages from the previous round carry the old `round` and are ignored.

## Leave behaviour

- **Exit** (in the bottom bar or on the result card) sends `leave` and then calls `onExit()`.
- **When the other player leaves:**
  - the game shows *"Your partner left the game."* with the final score and an Exit button
  - the board is frozen and no further moves, requests or rematches are accepted
- **If they come back:**
  - **Guest re-opens:** the host starts a brand-new session (new game id, round 1, scores 0, new fragile pieces) and sends it to the guest.
  - **Host re-opens:** its new copy has a newer game id, so the guest switches to the new game and the scores reset. Old snapshots from the previous game are ignored.
- **Unmounting:** the message subscription is cleaned up when the component unmounts (the unsubscribe function returned by `onMessage` is called).

## Integration into Gulaab

1. Copy the `dont-break-the-heart/` folder into Gulaab's `games/` folder.
2. Import it:

   ```tsx
   import Heartfall from "./games/dont-break-the-heart";
   import { meta as heartfallMeta } from "./games/dont-break-the-heart/meta";
   ```

3. Render it with the standard props, wiring `send` and `onMessage` to Gulaab's existing connection:

   ```tsx
   <Heartfall role={role} myName={me} peerName={peer} send={send} onMessage={onMessage} onExit={close} />
   ```

> **Note:** `meta.id` is `"dont-break-the-heart"`, as specified for this game. The Gulaab brief says ids should be *lowercase letters/numbers only*. If the game picker rejects hyphens, change the id to `"dontbreaktheheart"`; nothing else depends on it.

### Layout and accessibility notes

- **Layout:** `width: 100%`, `max-width: 384px`, `height: 420px`, `max-height: 100%`, transparent background. It works at 320 px wide with no scrolling.
- **Font:** inherited from the app.
- **Touch targets:**
  - Each piece's touch target is its own cell, extended past the heart outline for edge pieces. The smallest one measured in a real browser holds a **48 px** square, at both 320 and 384 px wide.
  - All buttons are at least 44 × 44 px.
- **Reduced motion:** under `prefers-reduced-motion: reduce`, all animations are switched off. Shattered pieces simply disappear and no confetti falls.
